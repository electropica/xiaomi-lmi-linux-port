# Mobian battery triage collector (Linux 7)

The collector writes JSONL at a default 300-second interval (minimum 30 seconds), with an exclusive output file and restrictive permissions. It reads battery sysfs counters, suspend/resume counters, logind inhibitor ownership, and process activity. Separately it observes logind `PrepareForSleep`, requests to logind methods, and, if accessible, GNOME ScreenSaver signals. A v4 short run on sector produced two samples in 30 seconds, stopped automatically, and attributed logind callers to `python` and `sshd`; this confirms the capture path for that run but says nothing about battery impact.

On the test handset, `/usr/local/lib/lmi-battery-triage/collector.py` and `lmi-battery-triage@.service` are installed for explicitly started, uniquely named investigations. The template has no enable target, so it does not start at boot. `systemd-analyze verify` and a short manual start/stop passed; no instance is left running. Captures are stored under `/var/lib/lmi-battery-triage/`, protected by a root-only directory and mode 0600 files. A new instance name must be used each time: an existing capture is never overwritten. The optional sleep hook remains uninstalled.

## Actionable comparisons

The first process pass establishes a baseline using one `/proc/PID/stat` read per process and does not read cgroups. Later passes compare cumulative CPU ticks by `(boot_id, pid, start_ticks)`; only the top 20 processes with nonzero interval CPU ticks are reported, and cgroup paths are read only for those leaders. Cgroup paths are cached for a live identity. `cpu_ticks_delta` measures observed CPU time, not power. New or short-lived processes without a prior baseline are omitted. `active_count` and `omitted_active` make the cap visible. Inspect inhibitors' `what`, `who`, `why`, and `mode`; only `block` inhibitors are listed as possible blockers, while `delay` inhibitors are observations. Compare suspend counters and resume reason within a single boot. Battery counters are device-level readings and may be missing, noisy, or gauge-derived.

Application attribution is deliberately conservative: desktop applications commonly live inside `app-*.scope`; the scope and process name are clues, not proof of a specific visible app. No watts or energy are assigned to individual processes. The collector does not read process command lines, environment, input events, or application data.

## Perturbation and limits

Sampling is coarse (minimum 30 seconds, default 300) and bounded (default eight hours). Every sample records `collection_duration_sec`; process enumeration and capped attribution also record `process_activity.collection_duration_sec`. These are elapsed collection times, not a direct CPU-energy cost, and the observation itself can affect idle behavior. The initial GLib idle sample is explicitly one-shot; subsequent samples use only the requested interval. D-Bus method arguments are retained in the JSONL and may contain network or session metadata: protect the capture as private. Request receive timestamps are preserved as `request_wall_utc` and `request_boottime`; callback recording and PID resolution can occur later, including after resume, so use the request timestamps for ordering. The collector cannot see GSD's internal timer decision when it makes no D-Bus call. ScreenSaver signals are corroborating UI state, not proof of panel state. It does not poll while suspended or attribute a wake to a process. Compare with an uninstrumented baseline.

GI/Gio is used for logind and event monitoring. Caller PID resolution is asynchronous, outside the D-Bus message filter, avoiding a blocking nested bus call; if the unique sender exits before lookup it is recorded as unresolved. Do not treat missing fields as zero. Protect the output as private operational data.

The current development version checks a `CLOCK_BOOTTIME` deadline at resume and each sample, in addition to its GLib timer. Time suspended counts toward this deadline, but no wake alarm is scheduled: a sleeping phone can only stop the collector once it wakes naturally. If resume notifications are unavailable, it stops at the next sample. The earlier installed version still uses only the GLib timer, which does not count time spent suspended; preserve its capture and stop it explicitly after replugging. Determine sleep intervals from independent system logs or pre/post sleep events, not timer expiration.

Analyze a capture with `python analyze.py CAPTURE.jsonl` (or `--json`). Older captures without `start_ticks` are accepted; process CPU attribution is omitted with an explicit warning. Samples with missing or different boot IDs are never joined for CPU or suspend-counter deltas. The report highlights observed CPU-time deltas, top-cap omissions, `block` sleep inhibitors seen without suspend-success progress, `delay` inhibitors separately, PID-to-comm/cgroup hints, logind requests, sleep/wake events, and battery endpoints. Findings are correlation cues and do not claim process power or prove causality.

For a shorter French report, run `python rapport.py CAPTURE.jsonl`. The optional `sleep_hook.py` records firmware counters at sleep boundaries, with important limits and installation precautions explained in `SLEEP-HOOK.md`; it is not installed by this project.

Synthetic tests: `python -m unittest discover -v`. Scenarios cover `/proc/stat` parsing, PID reuse exclusion, baseline-only first pass, top-process cap, cgroup caching, one-shot initial callback, inhibitor/no-suspend correlation, event extraction, report limitations and optional sleep-hook snapshots.

An entirely separate, optional pre/post systemd-sleep hook candidate is documented in [SLEEP-HOOK.md](SLEEP-HOOK.md). It is not enabled or installed by the collector. Its synthetic tests are `python -m unittest -v test_sleep_hook.py`.
