# ADSP stop experiment: safety review

On 22 November the handset exposed one remote processor, `remoteproc0`, named `adsp`, in the `running` state. The audio startup service relies on that ADSP; a running state does not establish the ADSP's electrical power or its sleep behavior. The exposed ADSP sleep statistics reported count 5 during the observation, without establishing a per-phase delta.

The initial stop/start experiment is not qualified. The Linux remoteproc framework uses a power reference count. In the examined 6.19 lmi reference, writing `stop` to the remoteproc sysfs state invokes `rproc_shutdown()`, which may decrement that count while the state stays `running`. A recovery helper that assumes `running` means no state changed could therefore fail to restore the original reference count. The same reference-counted shutdown behavior is described by the upstream framework documentation. The exact active 7.2.12 source and the complete chain of reference owners have not been established by this observation. No ADSP stop was performed; the draft test is explicitly blocked from execution.

See the [remoteproc framework documentation](https://docs.kernel.org/staging/remoteproc.html). Before a controlled stop, identify the exact active implementation, its clients and ownership, and design a recovery that handles a successful stop request even when the state remains `running`. Capture a physically unplugged witness first, use a single change, confirm actual state, and verify audio after restoration. Do not infer ADSP current from its `running` state.
